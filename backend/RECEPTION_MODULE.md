> **Scope:** The full hotel front‑desk / reception domain of FamousGate — reservations, bookings,
> rooms & room status, room types & rate plans, guests & guest folios, room payments,
> charge‑to‑room, the cashier "Room Bills" settlement path, breakfast pax, housekeeping,
> conference & catering bookings, and maintenance.

> (`backend/src/**`) **and** introspecting the **live production database** (Supabase Postgres via
> `DATABASE_URL`) on **2026‑07‑29**. All column lists, types, `CHECK` enums, foreign keys, triggers
> and row counts below are copied from the live schema, not from migrations or assumptions.

## 1. Architecture at a glance

```
                 ┌────────────────────────────────────────────────────────┐
   Landing site  │                     Express API (backend/src)          │
   Reception app │  /bookings   /rooms   /guests   /folios   /room-charge  │
   Cashier app   │  /conference /catering-bookings /housekeeping /maint.   │
                 └───────────────┬────────────────────────────────────────┘
                                 │  supabase-js  (config/database.ts)  +  pg pool (db.ts)
                                 ▼
             ┌──────────────────────────────────────────────────────────────┐
             │                 Supabase Postgres (public schema)             │
             │  bookings ─1:N─ reservations ─1:1─ folios ─1:N─ transactions  │
             │      │              │                  │                       │
             │    rooms  ◄──── room_id            folio_transactions (audit)  │
             │   room_types                        folio_payments/folio_items │
             │    guests                           accommodation_breakfast_pax│
             └──────────────────────────────────────────────────────────────┘
```

**Two-layer booking model.** Every stay is stored twice, on purpose:

- **`bookings`** — the *parent commercial record*. Created first by
  [`booking.service.ts`](src/services/booking.service.ts) `createBooking()`. Supports
  `booking_type IN ('room','conference','outside_catering')`.
- **`reservations`** — the *operational front-desk record* that reception actually works with
  (check-in, check-out, charge-to-room, room status). `reservations.booking_id → bookings.id`
  (`ON DELETE CASCADE`). Almost all reception controllers query **`reservations`**, not `bookings`.

The [`Booking` model](src/models/Booking.ts) maps the `Booking`/`IBooking` TS class **onto the
`reservations` table** (`findById`, `save`, etc. all target `reservations`). Do not be misled by the
class name — "Booking" in code == a `reservations` row.

**Confirmation numbers.** `Booking.generateBookingNumber()` produces `HTL<YYMMDD>-<NNNN>`
(e.g. `HTL260729-0007`). A DB trigger derives `reservations.short_code` from it. The `HTL` prefix is
how the cashier station recognises a hotel bill (see §7).

## 4. The folio / room-bill data model (how a guest bill is stored)

A guest's **room bill** = one `folios` row keyed by `reservation_id`, holding four charge buckets:

```
total_charges  ≈ room_charges + food_charges + beverage_charges + other_charges
total_payments  = deposit/cashier payments + folio payment transactions
balance_due     = total_charges − total_payments     (== balance, mirrored)
```

- **`room_charges`** = accommodation (seeded from `reservations.total_amount` on folio creation).
- **`food_/beverage_/other_charges`** = Charge-to-Room POS charges, bucketed by outlet name/type
  (`resolveChargeBucket()` in [room-charge.controller.ts:57](src/controllers/room-charge.controller.ts#L57)).

Two ledger tables record activity against a folio:

| | `transactions` | `folio_transactions` |
|---|---|---|
| Role | Financial ledger (drives totals) | Audit trail (rich metadata) |
| Trigger | `recalc_folio_totals` recomputes folio `total_charges`/`total_payments`/`balance_due`/`balance` on every insert/update/delete | none |
| Written by | folio settle, `postRoomCharge`, `Folio.addTransaction` | `postRoomCharge`, `reverseRoomCharge` |
| Columns | minimal (§3.8) | rich (§3.9) |

> **⚠ Consistency nuance (important for anyone touching this):** the accommodation `room_charges`
> is **not** written as a `transactions` charge row — it lives only in the `folios` bucket column.
> But `recalc_folio_totals` sets `total_charges = SUM(transactions WHERE type='charge')`, i.e. it
> counts only POS charge-to-room rows, **excluding** the accommodation amount. To compensate,
> `postRoomCharge` and `getFolio` explicitly re-write `total_charges = room + food + bev + other`
> **after** the trigger fires, and `getFolio` reconciles read values with `Math.max(stored, computed)`
> (see [folio.controller.ts:73-113](src/controllers/folio.controller.ts#L73)). Net effect: after a
> charge-to-room the app-level update wins; but a raw `transactions` insert alone would understate
> the balance by the accommodation amount. Keep the app-side recompute whenever you add ledger rows.

## 5. Database triggers (business logic that runs in Postgres)

Introspected live on core reception tables:

| Table | Trigger | When | Function → effect |
|---|---|---|---|
| `reservations` | `trg_reservation_short_code` | BEFORE INS/UPD | `trg_fn_reservation_short_code()` → sets `short_code = extract_short_code(confirmation_number)` when blank |
| `reservations` | `trg_reservations_updated_at` | BEFORE UPD | `set_updated_at()` |
| `bookings` | `trg_sync_booking_cols` | BEFORE INS/UPD | `_sync_booking_cols()` → fills date aliases (`check_in_at` default 14:00, `check_out_at` 10:00), `pax = max(1, adults+children)`, `confirmation_number`↔`booking_number`, `room_rate ← subtotal` |
| `bookings` | `trg_booking_status_history` | AFTER UPD | `_record_booking_status()` → inserts into `booking_status_history` on status change |
| `bookings` | `trg_increment_guest_visits` | AFTER UPD | `_increment_guest_visits()` → `guests.total_visits += 1` when status becomes `checked_out` |
| `bookings` | `trg_bookings_updated_at` | BEFORE UPD | `set_updated_at()` |
| `rooms` | `trg_sync_room_cols` | BEFORE INS/UPD | `_sync_room_cols()` → `type_id = room_type_id`, `is_clean = housekeeping_status IN ('clean','inspected')` |
| `rooms` | `trg_room_status_history` | AFTER UPD | `_record_room_status()` → inserts into `room_status_history` on status change (this is why it has 409 rows) |
| `rooms` | `trg_rooms_updated_at` | BEFORE UPD | `set_updated_at()` |
| `folios` | `trg_sync_folio_balance` | BEFORE INS/UPD | `sync_folio_balance()` → `NEW.balance := NEW.balance_due` |
| `folios` | `trg_folios_updated_at` | BEFORE UPD | `set_updated_at()` |
| `transactions` | `trg_recalc_folio_totals` | AFTER INS/UPD/DEL | `recalc_folio_totals()` → recomputes owning folio's `total_charges`,`total_payments`,`balance_due`,`balance` |

`recalc_folio_totals()` body:
```sql
total_charges  = SUM(amount) WHERE type = 'charge'
total_payments = SUM(ABS(amount)) WHERE type IN ('payment','refund')
balance_due = balance = total_charges − total_payments
```

> **Takeaway:** status-history tables and guest visit counts are **automatic** — don't insert into
> `room_status_history`/`booking_status_history` manually (the service does a redundant manual insert
> into `room_status_history` in `updateRoomStatus`, which the trigger also does; both fire).

| POST | `/room-charge/folio/:reservationId/settle` | `settleRoomBill` | **Cashier settles the room bill** — inserts a `transactions` payment row; trigger drops the balance. |

**Feature gating for charge-to-room** (`branch_features` table, `postRoomCharge`):
- Parent flag `GUEST_ROOM_CHARGING` must be enabled for the branch.
- Per-outlet flag: `RESTAURANT_ROOM_CHARGING` (default), `EXECUTIVE_BAR_ROOM_CHARGING`
  (outlet name contains EXEC/EXECUTIVE), or `SPORTS_BAR_ROOM_CHARGING` (contains SPORT/SPORTS).

**In-house eligibility** (`isCurrentInHouseStay`): status ∈ `checked_in/checked-in/in-house/active`,
and `check_in_date ≤ today ≤ check_out_date` (check-out **day inclusive** — a guest can still charge
on the morning they leave), and stay ≥ 1 night. `today` is **Africa/Nairobi**.

`postRoomCharge` also **settles the source POS bill** across every possible outlet system
(`settleRoomChargeSourceBill`): `pos_shift_orders`, `unpaid_bills`, `shift_transactions`,
`pos_master_bills`, `restaurant_orders`, `bar_orders`, `pos_orders` — marking the bill `paid` with
method `ROOM_CHARGE` so it disappears from that outlet's cashier list.

## 7. Cashier ↔ Reception integration (Room Bills & hotel payments)

In [cashier.controller.ts](src/controllers/cashier.controller.ts):

- **Hotel bills are pulled out of the general Unpaid Bills list.** `getUnpaidBills` builds
  `mappedHotel` from unpaid `reservations` (`bill_type:'hotel'`, `is_hotel:true`) but **excludes**
  them from the combined list unless `?bill_type=hotel` is passed
  ([cashier.controller.ts:4013-4022](src/controllers/cashier.controller.ts#L4013)). Hotel room bills
  now live in the dedicated **Room Bills** area (`/room-charge/eligible-guests`), not Unpaid Bills.
- **Bill lookup resolves `HTL…` confirmation numbers** to a hotel reservation + folio
  (`getBillDetails` → `fetchHotelBillResponse`): it itemises accommodation + each charge-to-room POS
  bill from `folio_transactions`, computes `paidAmount = max(amount_paid, deposit) + folio payments`,
  and returns a `type:'hotel'` bill the cashier can settle.
- **Hotel payment path** (`processPayment`, HTL prefix): inserts into `payments` (`booking_id =
  reservation.id`), and when fully paid flips `reservations.payment_status='paid'`, `deposit_paid=true`;
  links the payment to the active cashier shift. A folio auto-settle also runs on cashier payment.
- **Room-bill settle** (`settleRoomBill`, `/room-charge/folio/:id/settle`): the cashier records the
  payment straight onto the folio via a `transactions` payment row → `recalc_folio_totals` reduces
  the balance. *Known gap (from project memory):* this folio payment does **not yet** post into the
  cashier's shift collections/reconciliation ledger — cash taken on a room bill won't show in "Shift
  Collections". Follow-up work.

## 8. Key end-to-end flows

### 8.1 Create booking (`POST /bookings` → `bookingService.createBooking`)
1. Resolve room (specific `roomId` verified free for dates, or first available of the type).
2. `createOrFindGuest` (dedupe by email) → `guests` row.
3. `Booking.generateBookingNumber()` → `HTL…`.
4. `calculatePricing` — inclusive model: `total = (base_rate + mealPlanCost) × nights`; back-solve
   `base = total/1.26`, VAT 16%, service charge 10%.
5. Insert **`bookings`** parent (`booking_type:'room'`, `status:'confirmed'`).
6. Insert **`reservations'** child (`Booking.save()`), linked via `booking_id`.
7. Room → `reserved` **only if check-in is today**.
8. Create **`folios`** row (`status:'open'`, `room_charges = total`).
9. Fire-and-forget confirmation email (Gmail SMTP).

### 8.2 Check-in (`checkInBooking`)
Guard: reservation must be `confirmed`. → `status='checked_in'`, `checked_in_at/by`; room →
`OCCUPIED` (via `bookingService.updateRoomStatus`, which logs `room_status_history`); welcome email.

### 8.3 Check-out (`checkOutBooking`)
Allowed from any active status. → `status='checked_out'`, `payment_status='paid'`,
`amount_paid=total`, `deposit_paid=true`, `checked_out_at/by`. **Auto-settles the folio**
(`status='closed'`, `settled=true`, `balance/balance_due=0`, `total_payments=total`). Resets the room
by **both `id` and `room_number`** to `status='available'`, `hk_status='vacant_clean'`,
`current_guest=null`. Invoice email. *(This is the fix behind the two most recent commits — checked-out
guests no longer linger in Room Bills / Rooms board.)*

### 8.4 Charge-to-Room (`postRoomCharge`) — see §6.4 gating + §4 storage.
Feature-gated → validate in-house → gross amount → find/create open folio → insert `transactions`
charge row (trigger recomputes) → app re-write of bucket + totals → insert `folio_transactions` audit
row → settle the source POS bill everywhere → invalidate bill cache → `audit_logs` entry.

### 8.5 Breakfast pax (`getDailyBreakfastPax` / `upsertDailyBreakfastPax`)
Snapshot of every `checked_in` reservation in-house on the breakfast morning (check-out day inclusive),
each with its real `meal_plan` + a `breakfast_eligible` informational flag (Deluxe/Executive/VIP room
types are auto-eligible). Reception confirms/locks the headcount into `accommodation_breakfast_pax`.

## 9. Gotchas / cautions for future work

1. **"Booking" class = `reservations` table.** `bookings` is the parent record; reception logic reads
   `reservations`.
2. **Folios have two balance columns** (`balance_due` canonical, `balance` mirror) and **two ledgers**
   (`transactions` drives totals via trigger; `folio_transactions` is audit). Accommodation isn't a
   `transactions` row — always re-derive totals app-side after inserting ledger rows (§4).
3. **`payment_status` on `reservations`** exists in DB but is commented out of `Booking.save()`; the
   cashier path writes it directly.
4. **`rate_plans` code path is stale** — `calculatePricing` references `is_percentage/multiplier/
   fixed_amount` columns that don't exist live; live plans use `rate_per_night`.
5. **Room dual columns** (`room_type_id`/`type_id`, `housekeeping_status`/`hk_status`/`is_clean`) —
   keep in sync; joins use `type_id`.
6. **Nairobi time everywhere** — in-house/breakfast date math uses `Africa/Nairobi`, not UTC.
7. **Room-bill settle isn't wired into cashier shift reconciliation yet** (§7).
8. **DB access for scripts:** `pg` + `process.env.DATABASE_URL` + `ssl:{rejectUnauthorized:false}`
   from `backend/`. `db.ts` has an 8s per-query timeout & pool max 10 — batch heavy introspection.
