Production Logging should be a **separate screen inside Kitchen Sessions** used only for **TRUE_BATCH_PRODUCTION items**.

It is **not** for normal items like chips, beef stew, ugali, rice, chicken curry, etc. Those are controlled by POS sales and recipe standards.

---

# Production Logging Screen

## 1. Purpose of the screen

The function of Production Logging is:

```text
To record when raw kitchen stock is converted into a new finished/intermediate stock item before sale.
```

Examples:

```text
Mangoes → Mango juice
Flour → Chapatis
Flour + sugar + eggs → Cake
Tomatoes + onions + spices → Sauce
Dough → Mandazi
```

So the screen answers:

```text
What raw stock was used?
What finished item was produced?
Was the output normal, short, or surplus compared to the standard?
```

---

# 2. Where it should open from

In Kitchen Sessions:

```text
Kitchen Sessions
→ Production Logging
```

Or from the active session header:

```text
[Production Logging]
```

When clicked, it should open:

```text
Production Logging Screen
```

This screen must automatically attach to:

```text
current branch
current kitchen_shift_id
current sub-shift: Shift A / Shift B / Single Shift
current business date
logged-in storekeeper
```

Storekeeper should not manually choose the shift.

# 6. Raw input table logic

After selecting the produced item, the system should load the standard raw inputs automatically.

Example:

```text
Produced Item: Mango Juice

System loads:
- Mangoes
- Watermelon
- Sugar
```

The storekeeper does not choose the recipe.

The storekeeper only enters actual quantity used.

Table:

```text
| # | Raw Item | Available Qty | Qty Used | Unit |
| 1 | Mangoes | 15kg | 10kg | kg |
| 2 | Watermelon | 5 pcs | 1 pc | pcs |
| 3 | Sugar | 10kg | 0.5kg | kg |
```

Rules:

```text
- Raw items come from the accountant standard.
- Unit loads automatically from DB.
- Available quantity loads from current kitchen stock.
- Storekeeper enters Qty Used only.
- Qty used cannot exceed available kitchen stock unless override exists.
```

---

# 7. Actual output section

Storekeeper enters what the chef reported.

Example:

```text
Actual output produced: 22 litres
```

The expected output is calculated by the system.

Example standard:

```text
10kg mangoes + 1 watermelon = 25 litres juice
```

If storekeeper enters:

```text
Actual output = 22 litres
```

System calculates:

```text
Variance = Actual - Expected
Variance = 22L - 25L
Variance = -3L
```

Important:

```text
Production variance must be signed.
Shortage = negative.
Surplus = positive.
Do not clamp production variance to zero.
```

---

# 8. Variance logic

Production variance formula:

```text
Actual Output - Expected Output = Production Variance
```

Example shortage:

```text
Expected output: 25L
Actual output: 22L
Variance: -3L
```

Example surplus:

```text
Expected output: 25L
Actual output: 27L
Variance: +2L
```

Both must be shown.

Why?

```text
Shortage shows under-production or loss.
Surplus shows better-than-standard yield and must remain visible for review.
```

---

# 9. Reason note logic

If variance is within tolerance:

```text
Save normally.
Reason optional.
```

If variance exceeds tolerance:

```text
Reason required.
```

Example:

```text
Expected: 25L
Actual: 22L
Variance: -12%
Tolerance: ±5%
Reason required.
```

Storekeeper enters:

```text
Reason: Some mangoes were overripe and pulp was low.
```

Then save is allowed.

---

# 10. Save behavior

When user clicks **Save Production Log**, the system should:

```text
1. Validate active kitchen shift exists.
2. Validate item is TRUE_BATCH_PRODUCTION.
3. Validate selected item has production/yield standard.
4. Validate raw inputs are from the standard.
5. Validate Qty Used > 0.
6. Validate Actual Output > 0.
7. Calculate expected output.
8. Calculate production variance.
9. Require reason if outside tolerance.
10. Save production log.
11. Deduct raw inputs from current kitchen shift stock.
12. Credit finished produced stock.
13. Refresh production history.
14. Refresh kitchen stock balance.
```

# 13. Role rules

Only these roles can log production:

```text
branch_storekeeper
storekeeper
kitchen_operations
```

Read-only roles can view production logs only:

```text
branch_accountant
branch_manager
super_admin
auditor
```

Blocked roles:

```text
chef
cook
waiter
general kitchen roles
```

Chef is attribution only. Chef does not log into the system to post production.

---

# 14. Important restrictions

Do not allow storekeeper to:

```text
- create recipe standards
- edit recipe standards
- choose arbitrary raw inputs outside the standard
- create new inventory items
- log production for normal direct kitchen items
- manually choose Shift B
- log production without active kitchen shift
```

# 16. Simple final rule

```text
Production Logging is only for batch-produced items.

Storekeeper enters:
- raw quantity used
- actual output produced
- chef attribution
- reason if variance exists

Accountant owns:
- production/yield standard
- serving/portion standard
- tolerance

System calculates:
- expected output
- actual vs expected variance
- finished stock balance
```

So the screen should be **a controlled production ledger**, not a free-entry recipe screen.
